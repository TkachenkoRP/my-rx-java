## О проекте

**MyRxJava** — это образовательная реализация ключевых концепций реактивного программирования (Rx-style).
Библиотека не стремится заменить промышленные решения (RxJava, Reactor), а служит для понимания внутреннего устройства
реактивных потоков:
как данные передаются от источника к подписчику, как операторы трансформируют потоки и как планировщики (`Schedulers`)
управляют многопоточностью.

## Архитектура системы

Архитектура построена на принципе "цепочки ответственности" (Chain of Responsibility), где каждый оператор оборачивает
предыдущий, создавая направленный граф обработки данных.

### Основные компоненты

| Компонент                      | Описание                                                                                                                         | Роль в потоке                                                                                        |
|--------------------------------|----------------------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------|
| **`Observable<T>`**            | Источник данных, который может генерировать элементы, ошибку или сигнал завершения.                                              | **Поставщик**. Предоставляет API для создания (`create`, `just`) и преобразования (`map`, `filter`). |
| **`Observer<T>`**              | Потребитель данных, реализующий методы `onNext`, `onError`, `onComplete`.                                                        | **Потребитель**. Именно здесь происходит конечная обработка результата.                              |
| **`Emitter<T>`**               | Интерфейс, связывающий `Observable` и `Observer`. Позволяет отправлять данные и проверять статус подписки (`isDisposed`).        | **Канал связи**. Абстракция для безопасной передачи данных.                                          |
| **`Disposable`**               | Объект, представляющий собой активную подписку. Позволяет отменить её в любой момент.                                            | **Контроллер**. Управляет временем жизни потока.                                                     |
| **`ObservableOnSubscribe<T>`** | Функциональный интерфейс, который содержит логику генерации данных. Передается в `Observable.create()`.                          | **Фабрика**. Ленивое определение источника.                                                          |
| **`Scheduler`**                | Абстракция для управления потоками выполнения. Определяет, где будет исполняться код (в `subscribeOn` и `observeOn`).            | **Планировщик**. Разделяет логику и инфраструктуру.                                                  |
| **`Worker`**                   | Внутренний компонент `Scheduler`, представляющий собой изолированный исполнитель. Может быть использован для сериализации задач. | **Исполнитель**. Выполняет переданные `Runnable` задачи.                                             |

### Поток данных

1. **Создание** — Observable.create() или Observable.just().
2. **Преобразование** — операторы map, filter, flatMap возвращают новый Observable, не изменяя исходный.
3. **Планирование** — subscribeOn() и observeOn() управляют потоками выполнения.
4. **Подписка** — subscribe() активирует поток. Возвращается Disposable для отмены.

## Schedulers: Управление потоками

Главная задача `Scheduler` — обеспечить *асинхронность*, не заставляя разработчика напрямую работать с `Thread` и
`ExecutorService`.

### Принцип работы

Каждый `Scheduler` инкапсулирует пул потоков (`ExecutorService`). Метод `execute(Runnable task)` просто передает задачу
в этот пул.
Более интересен метод `createWorker()`, который создает `Worker`. `Worker` гарантирует последовательное выполнение всех
задач,
переданных ему через его собственный метод `execute()`. Это ключевой механизм для `observeOn`, который должен
обрабатывать элементы в строгом порядке.

### Виды Schedulers

| Планировщик                | Пул потоков                                                          | Исполнение                                                | Область применения                                                                                                           |
|----------------------------|----------------------------------------------------------------------|-----------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------|
| **`ComputationScheduler`** | Фиксированный, размером `Runtime.getRuntime().availableProcessors()` | Параллельное                                              | **CPU-bound задачи**: обработка больших данных, математические вычисления, шифрование. Не подходит для блокирующих операций. |
| **`IOScheduler`**          | Кэшируемый (`newCachedThreadPool`)                                   | Параллельное, с созданием новых потоков при необходимости | **Блокирующие I/O**: чтение/запись файлов, сетевые запросы, работа с БД. Потоки переиспользуются, если свободны.             |
| **`SingleScheduler`**      | Один поток (`newSingleThreadExecutor`)                               | Последовательное                                          | **Синхронизация**: когда важен порядок обработки или нужен доступ к разделяемому ресурсу без гонок данных.                   |

### Правила использования

* **`subscribeOn(Scheduler)`**: Определяет поток, в котором выполняется исходный код `Observable` (логика внутри
  `create`). Работает на весь поток "вверх" от места вызова. Может быть вызван несколько раз, но важен только первый.
* **`observeOn(Scheduler)`**: Определяет поток, в котором будут обрабатываться результаты последующих операторов.
  Работает на весь поток "вниз" от места вызова. Может быть вызван несколько раз для смены контекста на разных этапах.

## Операторы преобразования

| Оператор                | Назначение                                                                             | Реализация                                                                                                                                                    |
|-------------------------|----------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **`map`**               | Преобразует каждый элемент потока в другой объект.                                     | Создает `MapOperator`, который применяет функцию `mapper` к каждому элементу.                                                                                 |
| **`filter`**            | Пропускает только те элементы, которые удовлетворяют условию.                          | Создает `FilterOperator`, который проверяет `predicate`. Если условие ложно, элемент не передается дальше.                                                    |
| **`flatMap`**           | Преобразует элемент в новый `Observable` и "сплющивает" его элементы в выходной поток. | Создает `FlatMapOperator`. Это самый сложный оператор, который управляет счетчиком активных внутренних подписок (`AtomicInteger`) для корректного завершения. |
| **`onErrorResumeNext`** | Перехватывает ошибку и переключается на резервный `Observable`.                        | Создает специальный `Observer`, который при получении `onError` подписывается на резервный источник.                                                          |

## Тестирование

Тестирование реактивных потоков имеет свою специфику, связанную с асинхронностью.

### Стратегия тестирования

В проекте используется модульное тестирование с `JUnit 5`. Ключевые принципы:

* **Блокировка (Latching)**: Для асинхронных тестов используется `CountDownLatch`, чтобы главный поток теста ждал
  завершения всех асинхронных операций.
* **Проверка состояний (State Verification)**: Используются `AtomicReference` для захвата ошибок и `AtomicBoolean` для
  флагов завершения.
* **Изоляция**: Каждый тест создает свои собственные коллекции (`ArrayList`) для сбора результатов, чтобы избежать
  влияния между тестами.

### Основные сценарии тестов

1. **Базовые сценарии (Тесты 1, 12, 13)**:
    * Создание через `create` и `just`.
    * Корректная доставка всех элементов и сигнала `onComplete`.
    * Проверка, что после `onComplete` или `onError` данные не передаются.

2. **Операторы (Тесты 2, 3, 4, 5)**:
    * `map`: Проверка преобразования типов и значений.
    * `filter`: Проверка корректной фильтрации по нескольким условиям.
    * `flatMap`: Проверка "сплющивания" списков в последовательность.
    * Комбинация: Проверка цепочек операторов.

3. **Обработка ошибок (Тесты 6, 7, 14)**:
    * Перехват ошибки из `create`.
    * Восстановление после ошибки (`onErrorResumeNext`).
    * Перехват исключений, выброшенных внутри `map`.

4. **Многопоточность и планировщики (Тесты 9, 10, 11, 15)**:
    * `subscribeOn`: Проверка, что код источника выполняется в потоке `IOScheduler`.
    * `observeOn`: Проверка, что обработка (в `subscribe`) выполняется в потоке `ComputationScheduler`.
    * Комбинация: Убеждаемся, что производство и потребление идут в разных потоках.
    * Стресс-тест: Запуск большого количества элементов в многопоточном окружении для проверки гонок данных.

5. **Управление подпиской (Тест 8)**:
    * Проверка, что `dispose()` прерывает генерацию данных.
    * Проверка, что `isDisposed()` корректно отражает состояние.

## Заключение

* Реализованная библиотека MyRxJava демонстрирует:
* Основы реактивного программирования: ленивые вычисления, push-модель, поток данных.
* Паттерн "Наблюдатель" (Observer): в чистом виде с расширениями для асинхронности.
* Композицию операторов: неизменяемость цепочек, создание новых объектов для каждого преобразования.
* Асинхронность и многопоточность: через продуманную архитектуру Scheduler и Worker.
* Graceful degradation: обработка ошибок без падения всего приложения и возможность отмены подписки.
